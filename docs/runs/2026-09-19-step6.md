## Verdict

1. Both wide checkpoints pass all four acceptance bars and the energy bound, but neither
   improves on model20's scores at matched-horizon eval — widening to 256/6 (5.4M params,
   5.5x model20) did not buy accuracy on this task/eval at the wall-clock spent.
2. Per the BEST rule (docs/GOAL-2026-09-19.md), BEST must be a projection-ON-in-training checkpoint that
   passes all four bars: model20 is the only one whose training run doc's launch command
   contains both `--project true` and `--project-energy true` (`docs/runs/2026-09-19-2.md`);
   `model-wide-1`/`model-wide-2` trained with `--project true` only (energy projection not
   explicitly enabled during training). **BEST = model20.**
3. Task 4's convergence criterion (a comparison table naming a BEST, with BEST required to
   be a projection-ON-and-passing checkpoint) is met: this doc is that table, and the
   named BEST is model20 — the wider models are ineligible for BEST despite passing the
   eval bars, because they weren't trained with energy projection ON.

## Addendum 2026-09-20: bias (the color-offset the author saw in the gallery)

The author's gallery observation: model-wide-1 renders with a uniform blue background and
model-wide-2 a uniform pink one while their corr reads 0.997 — a constant offset in `h`
that correlation cannot see. Added `bias = (mean(h_model) - mean(h_solver)) / std(h_solver)`
to `crates/train/src/metrics.rs::Metrics` (amplitude = the solver field's standard
deviation, not max-min), to `eval-metrics`'s per-horizon table, and to the gallery's
compare-mode metrics line ("bias +0.12" under each panel).

`./target/release/jacobi eval-metrics --model artifacts/<name> --horizons 10,25,50
--trajectories 24 --seed 0 --project <true|false> --project-energy <true|false>`, mean
bias over 2 scored (pre-reflection) trajectories at each horizon:

| model | bias@10 ON | bias@25 ON | bias@50 ON | bias@10 OFF | bias@25 OFF | bias@50 OFF |
|---|---:|---:|---:|---:|---:|---:|
| model20 | +0.000 | +0.000 | +0.000 | -0.149 | -0.509 | -0.860 |
| model-wide-1 | +0.000 | +0.000 | +0.000 | -0.691 | -2.337 | -3.917 |
| model-wide-2 | +0.000 | +0.000 | +0.000 | +0.729 | +2.464 | +4.151 |

**Diagnosis**: mass projection (`project_mass`, `crates/jacobi2000/src/project.rs`) acts
directly on channel 0 (`h`) — it shifts the normalized `h` channel's box mean back to the
value recorded at the last reset, which is the same affine transform as shifting physical
`h` by a constant. With projection ON, bias is exactly 0.000 for all three checkpoints at
every horizon, including model-wide-1/-2 (which were trained with `--project true` but
without `--project-energy true` — energy projection is irrelevant to this metric; mass
projection alone zeroes it). With projection OFF, bias grows with horizon and is 4-6x
larger for the wide checkpoints than for model20 at 50 ticks — consistent with a raw
(unprojected) proposal from a wider, more capable model drifting in mean faster, not with
an offset baked into a specific channel.

The CLI confirms the fix is a projection issue, not a checkpoint issue. Checking whether
the page applied the same projection that removes it in the CLI: `App`'s default
(`crates/web/src/lib.rs`) is `mass_projection: true`, matching `web/index.html`'s `t-mass`
checkbox (`checked` by default), and no code path resets it when switching models or
entering/leaving compare mode — the toggle default was already correct in the page. The
gap was the metric itself: bias wasn't computed or shown anywhere in the page, so the author's
visually-obvious color offset had no number attached to it (this run adds one). See
`web/test/gallery.mjs`'s compare-mode assertion (`|bias@30, model20| < 0.05`) for the
headless confirmation that the live page's bias matches the CLI's zeroed-by-projection
result with the default toggle state.

**Acceptance bar added**: `|bias| <= 0.05` at 50 ticks, projection ON (model20's own
number is 0.000; the four-bar table above is extended to five bars).
