# Roadmap item 3 — forward time with bigger steps

Machine: data generation on an Apple M2 (native, CPU); training on a Linux
desktop with an RTX 3080 (CUDA), under `flock`, no other GPU job running.

## What this is

CONCEPT.md section 15 ("Multi-horizon operators"): "A solver must step; a
learned operator need not... Horizon as input: dt is already conditioning --
train on (state_t, state_{t+k}) with random k... Measure: error vs horizon
for direct k-step prediction against k one-step applications; wall clock per
physical time. If direct-8 ~= 8x single-step, we do 8x less work per unit of
physical time -- a claim a solver cannot make."

Minimal form for tonight, stated up front: fixed `k=8`, not random `k` as an
input (the natural next rung -- flagged as not done). Same `Jacobi2000`
architecture and stencil mask as the existing patch-transformer, warm-started
from the curriculum baseline (`exports/curriculum/s6-mass-energy-proj`), but
trained so one `model.step()` call jumps 8 solver ticks (target =
`state[t+8]`, not `state[t+1]`).

## Training

```
python -m jacobi2000_pt.bigstep --dataset data/sw-nu001 --out results/bigstep \
  --baseline exports/curriculum/s6-mass-energy-proj --k 8 --steps 2000 --lr 1e-4 --batch 16 \
  --n-repeats 5 --eval-trajectories 16
```

995,843 params (unchanged architecture). Wall clock: **37.1 s** on the 3080.

## Comparison

Same total physical horizon (40 ticks = 5 x direct-8, or 40 x baseline-1),
16 held-out trajectories, correlation and wall clock for the forward passes
only (no data loading):

| | mean corr @ 40 ticks | total wall (16 trajectories) | forward passes |
|---|---:|---:|---:|
| direct-8 (this run) | 0.6966 | 0.188 s | 5 per trajectory |
| baseline (curriculum s6, 1 tick/call) | 0.7464 | 1.305 s | 40 per trajectory |

**6.9x less wall clock** for 40 ticks of physical time (0.188 / 1.305), at
93% of the baseline's correlation (0.6966 / 0.7464) -- close to, not quite,
the "direct-8 ~= 8x single-step for ~= the same accuracy" claim CONCEPT
poses. Full per-trajectory rows (including RMSE): `results/bigstep-log.json`.
Raw run log: `results/bigstep-run.log`. Checkpoint:
`results/checkpoints/bigstep/` (safetensors + config.json, gitignored --
same `Jacobi2000` tensor names as the baseline, so this one *could* be
imported into Burn with `jacobi import-weights` and scored by
`eval-metrics`, unlike items 1 and 2; not done tonight since `eval-metrics`
assumes one solver tick per model step and would silently misinterpret a
direct-8 checkpoint's horizons as 8x too short).

## Observations

- RMSE tells a clearer story than correlation: direct-8's RMSE is
  consistently 1.5-2x the baseline's (e.g. trajectory 0: 0.634 vs 0.327;
  trajectory 3: 0.620 vs 0.324) across nearly every trajectory, while
  correlation is a mixed bag (direct-8 *beats* the baseline on 6 of 16
  trajectories, e.g. trajectory 2: 0.531 vs 0.460, trajectory 5: 0.704 vs
  0.520). Read plainly: direct-8 tracks the right *shape* about as well as
  40 compounding single steps, but with a larger, fairly systematic
  amplitude error the correlation metric alone doesn't show.
- The wall-clock ratio (6.9x, not the theoretical 8x) is Python-loop
  overhead on 5 vs 40 calls, not a per-call cost difference -- both models
  are architecturally identical, so the marginal cost of a single forward
  pass is the same either way; the entire 8x should be recoverable in a
  tighter benchmark loop (not measured tonight).
- 2000 steps, one dataset, one seed, one `k` -- this is a smoke-to-real-run
  budget, not a converged direct-8 operator (the baseline itself is a
  6-stage curriculum; direct-8 got one 2000-step warm-started stage).
  Whether the accuracy gap closes with more training or is a structural
  property of jumping 8 ticks in one attention pass is open.
- Not attempted: random `k` as a conditioning input (section 15's actual
  proposal, one model answering "next/10th/40th"), the consistency loss
  (`predict 8 ~= predict 4 twice`), and importing this checkpoint into Rust
  for a proper `eval-metrics`-shaped horizon sweep (would need a horizon-
  aware CLI path, out of scope tonight).

## Follow-up (same night, later) — random-k conditioning

Implements section 15's actual proposal: one model, `k in {1,2,4,8}` drawn
at random each training step and appended (as `log(k)`) to the metadata
vector, instead of `bigstep.py`'s single fixed `k=8`. `training/jacobi2000_pt/
randomk.py`: `Jacobi2000Config.meta_dim` extended 5 -> 6 (a deliberate,
disclosed architecture change -- `meta.weight` is padded with one freshly-
initialized row, the rest of the body warm-started unchanged from the same
curriculum-s6 baseline `bigstep.py` used, so the two runs start from the
same converged body and differ only in the meta input and training target).
995,971 params (128 more than the fixed-k8 run's 995,843, from the one extra
meta input row).

```
python -m jacobi2000_pt.randomk --dataset data/sw-nu001 --out results/randomk \
  --baseline exports/curriculum/s6-mass-energy-proj --ks 1,2,4,8 --eval-k 8 \
  --steps 2000 --lr 2e-4 --batch 16 --n-repeats 5 --eval-trajectories 16
```

Wall clock: **37.1 s** on the 3080 (same step count and batch size as the
fixed-k8 run's 37.1 s -- training cost is identical per step regardless of
which `k` a given step draws).

Same eval as the original bigstep comparison (40-tick horizon, 16 held-out
trajectories, random-k model conditioned at k=8 and stepped 5 times vs. the
single-step baseline stepped 40 times):

| model | mean corr @ 40 | mean rmse @ 40 | total wall (16 traj) |
|---|---:|---:|---:|
| fixed-k8 (original bigstep run) | 0.6966 | -- (see original table) | 0.188 s |
| **random-k, conditioned at k=8** | **0.8934** | 0.2892 | 0.193 s |
| baseline (curriculum s6, 1 tick/call, 40 calls) | 0.7464 | 0.3957 | 1.337 s |

### Observation

Random-k conditioning **beats both** the fixed-k8 model and the single-step
baseline at k=8, at essentially the same wall clock as fixed-k8 (~7x less
than the baseline's 40-step rollout): mean corr 0.8934 vs fixed-k8's 0.6966
and the baseline's 0.7464, and lower RMSE than the baseline (0.289 vs
0.396) despite the earlier fixed-k8 run showing *higher* RMSE than baseline.
Plausible reason, not confirmed by an ablation tonight: training on a mix of
{1,2,4,8}-tick targets is a curriculum in disguise (the easy k=1 steps early
in a given epoch regularize the harder k=8 steps, similar in spirit to the
existing model20 lineage's own rollout curriculum, `docs/runs/2026-09-19-
{1,2}.md`), so it is not obviously surprising that training on several
horizons at once produces a better k=8 operator than training on k=8 alone
-- but this run cannot separate "multi-horizon training regularizes" from
"this particular 2000-step run of fixed-k8 was an unlucky draw" (one seed,
one run each). Full rows: `results/randomk-log.json`. Run log:
`results/randomk-run.log`. Checkpoint: `results/checkpoints/randomk/`
(gitignored, meta_dim=6, not importable into Burn without a config-schema
change, same caveat as the fixed-k8 checkpoint).

Not attempted: the consistency loss (predict-8 ~= predict-4-twice), scoring
at k values other than 8 (the model was trained on all of {1,2,4,8} but only
evaluated at k=8), and a repeat with a different seed to check whether the
fixed-k8-vs-random-k gap is a real effect or run-to-run noise.
